# M1 人工验收手册（E2b）

本手册依据 [02 采集](../design/02-capture.md) 第 4–6 节、[03 数据模型](../design/03-data-model.md) 第 2、4.3 节和 [09 里程碑](../design/09-milestones.md) 的 M1 验收项执行。E2a 交付离线断言与本手册；以下实机操作留给 E2b，完成后记录操作时间、断言结果和人工观察。

## 1. 会话准备与独立数据目录

前置条件：Windows 桌面会话、Deno 2.9.8、仓库指定的 Rust 工具链、当前 main 的 release 构建。先从托盘退出已有 Quartz；同一用户会话的核心互斥量不随数据目录变化。选定测试目录后，全程在同一 PowerShell 中操作，目录中只放验收数据。

```powershell
Set-Location D:\Documents\403F\Quartz
git branch --show-current
git rev-parse HEAD
cargo.exe build --release -p quartz --target-dir target/windows
if ($LASTEXITCODE -ne 0) { throw 'release build failed' }
$exe = (Resolve-Path .\target\windows\release\quartz.exe).Path
$acceptanceParent = Join-Path $PWD ('target\windows\acceptance-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $acceptanceParent | Out-Null
$previousLocalAppData = $env:LOCALAPPDATA
$env:LOCALAPPDATA = $acceptanceParent
$dataRoot = Join-Path $acceptanceParent 'Quartz'
$utf8 = [System.Text.UTF8Encoding]::new($false)
$core = Start-Process -FilePath $exe -PassThru
$core.Id
```

[DataDirectory::resolve](../../crates/quartz/src/data_directory.rs) 只读取 `LOCALAPPDATA`，要求绝对路径并追加 `Quartz`。上面的设置只影响当前 PowerShell 及其子进程，核心、dump、日志、锁与备份都使用 `$dataRoot`，数据库为 `$dataRoot\quartz.db`。当前没有专用 `--data-dir` 或 `QUARTZ_DATA_DIR`；已有环境变量足以隔离，不需要新增生产路径入口。会话结束时恢复 `$env:LOCALAPPDATA = $previousLocalAppData`。

启动成功后只有托盘图标和隐藏消息窗口。通过托盘右键菜单“退出”正常停止；不要点击“打开”或左键选择图标。托盘退出结束运行与事实，运行结束原因为 `user_exit`，前台和可用状态为 `shutdown`，时钟段为 `run_end`；系统关机路径使用 `shutdown`。确认 `$core.WaitForExit(10000)` 返回 true，再导出。强制终止只用于第 9 节指定的崩溃场景。

## 2. 每个场景的导出与自动断言

每个场景单独启动和正常退出核心，保留完整运行。下列函数调用 dump 时继承独立的 `LOCALAPPDATA`。日期使用 Windows 当前本地日历日；参数必须覆盖该运行访问过的全部日期，包括回拨后的日期、跨午夜相邻日和长锁屏期间的日期。

```powershell
function Export-Facts([string[]] $Dates, [string] $Output) {
    $lines = [System.Collections.Generic.List[string]]::new()
    foreach ($day in $Dates) {
        $part = @(& $exe dump --date $day --format json)
        if ($LASTEXITCODE -ne 0) { throw ('dump failed: ' + $day) }
        foreach ($line in $part) { $lines.Add($line) }
    }
    [System.IO.File]::WriteAllLines($Output, $lines, $utf8)
}
$dates = @((Get-Date -Format 'yyyy-MM-dd'))
$dump = Join-Path $acceptanceParent 'scenario.jsonl'
Export-Facts -Dates $dates -Output $dump
deno task acceptance $dump
if ($LASTEXITCODE -ne 0) { throw 'acceptance failed' }
```

也可将同一份 JSON Lines 通过标准输入传给 `deno task acceptance -`。多日 dump 的相同行按数据库类型和主键去重，冲突快照直接失败。核心运行时可检查开放行，但只检查各自确认点之前的范围；不推算确认点到当前时间的尾部。导出多个日期时，先正常退出核心，或用 Process Explorer 挂起核心，再连续导出。缺失日期导致的覆盖孔洞仍然失败，补齐导出后重新检查。

自动报告中的规则名：`format` 检查 JSON Lines、整数、端点和身份字段；`coverage` 按运行、时钟段顺序检查单调时长、前台与无前台事实、停止原因并集和缺口；`idle` 检查独立掩码与输入证据；`midnight` 检查已关闭事实的 UTC 午夜拆分、最长 24 小时和前台 `session_key`；`recovery` 对照 `--before` 检查崩溃恢复终点；`privacy` 检查字段删除；`clock` 检查段内 UTC 与 sequence 顺序。运行、时钟段是容器，可超过 24 小时；开放 availability 在结束时拆分，允许尚未拆分的长确认范围。运行行只有 UTC 端点，回拨时 duration_ms 可为负；守恒与负时长检查使用段内单调时间。睡眠时单调时钟不前进，恢复的 availability 墙上时间可以延伸到新段起点；重开 idle 行保留原检测证据。

每节完成操作后均执行本节的“正常退出 → Export-Facts → deno task acceptance”。自动断言检查存储结构和时长，事件是否完整、身份是否正确及真实操作到事实边界的延迟由人工核对。下文“需注入”的场景当前没有公开命令行入口，必须先准备隔离测试驱动；列出的现有 Rust 测试可验证相应逻辑，实机项保持待验收。

## 3. 快速 Alt-Tab、任务栏、多显示器、虚拟桌面（02 §6 第 1 项）

前置条件：两个标题可区分的窗口、两台显示器、两个 Windows 虚拟桌面；准备能记录 UTC 毫秒切换参考时间的测试窗口或外部测量工具。仓库尚未提供此参考采样工具，准备完成后才能测切换误差。

步骤：启动核心，按小于 200 ms 的间隔连续 Alt-Tab 至少 100 次；接着点击任务栏切换 20 次；将窗口移到另一显示器并切换 20 次；使用 Win+Ctrl+Left/Right 往返虚拟桌面 20 次。连续办公一小时，保留每次切换参考时间与起止 UTC。正常退出、导出全部日期并断言。

预期事实：窗口切换产生相接的 `foreground`，旧行通常为 `switch`；短暂桌面不可观察时允许 `no_foreground`，原因 `unknown_desktop`，恢复后立即复核；`sequence` 按运行内顺序增加。自动覆盖 `coverage`、`clock`、`privacy`。人工逐次核对实例和顺序，以事实起点减参考时间计算误差绝对值，将样本排序取第 `ceil(0.95 × N)` 项，要求 P95 < 100 ms。比较独立数据目录 `logs\core.log` 中 `missed_events` 计数在完整一小时内的增量，要求 ≤ 1。新运行从零计数，默认 INFO 日志在发生漏检时输出该计数。

## 4. 同一程序、同标题的两个窗口（02 §6 第 2 项）

前置条件：同一程序的两个顶层窗口，标题完全一致；记录窗口位置。步骤：启动核心，交替激活两个窗口各 20 次，每次停留一秒，最后正常退出、导出并断言。

预期事实：应用字段和标题相同，`window_instance_id`、`hwnd` 不同；每次切换结束原因为 `switch`，`sequence` 增加。自动覆盖 `coverage`、`clock`；人工核对不能合并成同一窗口实例，窗口销毁后重新创建时检查实例及 generation。

## 5. 浏览器标签、播放器每秒标题与终端（02 §6 第 3 项）

前置条件：浏览器两个标题不同的普通标签、每秒修改标题的测试播放器、可改变窗口标题的终端。步骤：启动核心，交替点击两个标签 20 次；在播放器前台连续运行 60 秒；切至终端执行 20 条改变标题的命令；每段记录参考标题和 UTC，正常退出、导出并断言。

预期事实：同一窗口实例内不同标题立即切段，旧行为 `title`，相同标题通知去重；短暂标题仍有事实。每秒变化本身不会超过“10 秒超过 50 次”的标题风暴阈值；另用每秒 10 次持续 10 秒验证风暴，未过载时保留每个已观测不同标题，过载时出现 `capture_gap/event_overload`。自动覆盖 `coverage`、`clock`、`privacy`。人工核对标题列表、通知去重和事件延迟；M1 网页上下文尚未接入，检查前台事实。

## 6. UWP、提权程序、UAC 与安全桌面（02 §6 第 4 项）

前置条件：可用的 UWP 程序、管理员终端和默认安全桌面 UAC。步骤：启动核心，分别激活 UWP 与管理员终端各 10 秒；发起一次需要提权的操作，在 UAC 提示停留 10 秒后取消；按 Ctrl+Alt+Del，停留 10 秒后取消。正常退出、导出并断言。

预期事实：UWP 优先使用内容应用 AUMID，普通提权窗口可解析时保留应用；查询失败使用 `unresolved` 身份和类名。UAC、安全桌面不可观察期间为 `no_foreground/unknown_desktop`，旧前台以 `no_foreground` 结束；返回后复核并新建事实。自动覆盖 `coverage`、`clock`、`privacy`。dump 输出应用显示名和 app_id；需要核对 AUMID 时，另用只读 SQLite 工具查询独立库的 `applications.identity_key`，并通过 app_id 对应到事实。人工核对 UWP 内容身份、保护窗口隐私字段及安全桌面通知覆盖；若未收到相应通知，记录实际缺失，不把上一窗口持续存在视为通过。UAC 与 Ctrl+Alt+Del 需要用户手动操作。

## 7. 锁屏、S0 睡眠、RDP 断开与重连（02 §6 第 5 项）

前置条件：`powercfg /a` 确认支持 S0 现代待机；另备 RDP 客户端和重连权限。步骤：启动核心，Win+L 锁屏一分钟并解锁；通过 Windows 电源菜单睡眠一分钟后唤醒；在 RDP 会话运行核心，断开客户端一分钟后重连。锁屏和睡眠各做 10 次，再正常退出、导出并断言。不支持 S0 的设备记录硬件前置条件未满足。

预期事实：旧前台以 `locked`、`suspended` 或 `disconnected` 结束，同名 availability 覆盖停止范围，解除时为 `resumed`。睡眠恢复关闭旧时钟段为 `resume`，旧段 availability 可能以 `clock_jump` 结束，在新段重新打开仍有效原因；没有停止原因且复核完成后才恢复前台。自动覆盖 `coverage`、`idle`、`midnight`、`clock`。人工核对睡眠墙上时间和单调时长的差异、RDP 重连没有擅自清除 locked/paused。睡眠和 RDP 操作需要用户在场。

## 8. 系统时间、跨午夜、空闲阈值（02 §6 第 6 项）

前置条件：可更改系统时间的隔离测试 Windows，会影响联网应用时先关闭这些应用；默认空闲阈值 180,000 ms。

步骤：第一轮启动核心，保持一个窗口前台，将系统时间前拨五分钟、再回拨十分钟，恢复正确时间后再正常退出，保证运行的 UTC 起止能被 dump 的日范围读取；导出所有访问过的日期并断言。第二轮在 UTC 23:59 前启动，保持同一前台到 UTC 00:01 后再退出，导出午夜两侧对应的本地日期并断言；本地午夜另做一轮，核对本地日历日 dump 边界。第三轮在前台不操作 179 秒后输入一次；再次不操作至少 185 秒，再输入，等六秒后退出、导出并断言。

预期事实：时变前旧事实以 `clock_jump` 结束，旧段为 `time_change`，新段使用新 UTC 锚点，仍有效 availability 在新段重开；顺序按 `(run_id, sequence)`。UTC 午夜前台旧行为 `midnight_split`，片段共享 `session_key`；关闭的 availability 同样拆分。空闲起点为 `last_input_utc_ms + threshold_ms`，证据含 `detected_utc_ms`、`policy_version`，前台在 idle 中继续存在，恢复检测延迟 ≤ 5 秒。自动覆盖 `coverage`、`idle`、`midnight`、`clock`；人工核对通知来源、时区变化只改查询日界、阈值附近是否提前空闲。改时、午夜等待与边界输入需要用户在场。

## 9. 强制结束、长锁屏崩溃、确认点与批量等待（02 §6 第 7 项）

前置条件：Process Explorer，能挂起和结束当前验收核心；确保选中的 PID 为 `$core.Id`。崩溃前快照必须在核心已挂起后导出，保证之后没有新的提交。

步骤：启动核心并活动至少 65 秒；在 Process Explorer 中挂起该 PID；执行 `Export-Facts -Dates $dates -Output (Join-Path $acceptanceParent 'before.jsonl')`；然后在 Process Explorer 中结束同一进程，或执行 `Stop-Process -Id $core.Id -Force`。重新执行 `$core = Start-Process -FilePath $exe -PassThru`，等两秒后从托盘退出，导出到 `after.jsonl`。

```powershell
$before = Join-Path $acceptanceParent 'before.jsonl'
$after = Join-Path $acceptanceParent 'after.jsonl'
Export-Facts -Dates $dates -Output $after
deno task acceptance $after --before $before
if ($LASTEXITCODE -ne 0) { throw 'crash recovery failed' }
```

再做长锁屏版本：锁定独立测试会话超过一天，另一个管理会话挂起原验收 PID、在相同独立 `LOCALAPPDATA` 下导出涵盖全部日期的 before，再结束并恢复原会话。旧锁屏行恢复后应拆成午夜片段。确认点加批量等待版本需测试驱动控制第 59 秒确认和最长一秒提交等待，在期限前后各终止一次；现有 `checkpoint_commit_deadline_preempts_the_batch_wait`、`crash_recovery_uses_each_rows_confirmation_and_splits_long_locked_mask` 测试提供逻辑验证。

预期事实：旧运行、旧开放段和所有旧开放事实以各自最后确认点关闭，最终片段为 `crash_recovered`，更早午夜片段为 `midnight_split`；确认点列清空；新运行编号增加，前台重新复核。两次运行之间的未采集范围保持空白，查询时解释为 `core_offline`。自动覆盖 `recovery`、`coverage`、`midnight`、`clock`；`--before` 按原行与午夜连续片段查找恢复终点，不要求所有行确认值相同。人工记录强制结束 UTC，核对正常写入条件下末次持久确认距强制结束 ≤ 60 秒；长锁屏实机与精确提交时机控制均需人工或注入驱动。

## 10. 叠加停止原因、启动已停止、通知重试（02 §6 第 8 项）

前置条件：独立测试驱动能依次提交 `StopChange`、初始会话查询结果和通知注册失败；当前托盘只有“打开”和“退出”，没有暂停入口，公开 CLI 也没有暂停或故障注入命令。

步骤：驱动先 Begin(paused) → Begin(locked) → End(locked) → End(paused)；再 Begin(suspended) → Begin(disconnected) → 恢复时钟边界 → End(suspended) → End(disconnected)。分别以初始 locked、初始 disconnected 启动，清除其原因。最后使会话通知注册失败一次，观察五秒后重试成功及前台复核。持久化每轮写入，再使用同格式 JSON Lines 导出、执行第 2 节断言；实机驱动准备前保持待验收。可先运行 `cargo.exe test -p quartz-domain stop_reason_union_requires_review_and_preserves_overlaps --target-dir target/windows` 和 `cargo.exe test -p quartz-domain startup_waits_for_session_query_and_registration_retry --target-dir target/windows`。

预期事实：同一原因有自己的 availability，允许 paused 与 locked、suspended 与 disconnected 重叠；只清除收到解除通知的原因，最后一个原因清除并复核后才开前台。注册失败到成功复核之间保持停止或等待范围，不能生成使用旧前台的事实，必须结算的未知范围按缺口记录。自动覆盖 `coverage`、`clock`；人工核对五秒重试、原因集合变化与前台恢复时机。睡眠叠加 RDP 需要用户配合；启动已锁定/断开需受控启动任务或测试驱动。

## 11. 主线程过载、写队列满、数据库故障（02 §6 第 9 项）

前置条件：隔离注入驱动，能阻塞接收端、填满 1,024 项主线程队列、填满采集到数据库队列、让 SQLite 写事务返回错误并恢复。当前没有用户可调用的注入开关；不要通过修改生产目录权限制造此故障。

步骤：先保留稳定前台和最后可信边界；暂停对应消费者，持续投递事件直到溢出；恢复消费并触发前台复核；对写队列重复。数据库版本先令连续写事务失败，持续到内存保留上限，再恢复写入和复核。每种故障单独结束运行、导出并断言。逻辑测试可执行 `cargo.exe test -p quartz --target-dir target/windows queue_capacity_discards_whole_batch_and_persists_identity_free_gap`、`cargo.exe test -p quartz --target-dir target/windows database_failure_retains_batches_then_writes_loss_before_new_facts`；主线程过载逻辑可用 `cargo.exe test -p quartz-domain --target-dir target/windows overload_gap_waits_for_review_and_splits_at_clock_boundary`。

预期事实：前台在最后可信边界以 `capture_gap` 结束，缺口分别为 `event_overload`、`write_queue_overload`、`database_error`；从实际丢失或不可信边界到恢复复核完成，缺口与可信事实相接，跨时钟段拆分，缺口先于新的事实持久化。不使用恢复后的最后标题填补旧缺口。自动覆盖 `coverage`、`privacy`、`clock`；人工把注入的可信/丢失/恢复时间对照缺口端点，检查内存保留上限与异常诊断。注入工具未就绪时该实机项保持待验收。

## 12. 挂起目标与超长标题、隐私求值（02 §6 第 10 项）

前置条件：可改变标题的独立测试窗口、Process Explorer、测试规则输入工具。准备 4,095、4,096、4,097 个 UTF-16 单元标题，以及截断边界落在高代理项后的非 BMP 字符；不要用 UTF-8 字节数代替 UTF-16 单元数。

步骤：启动核心，目标前台时从 Process Explorer 挂起目标进程，切换离开再返回，记录核心事件回调耗时后恢复目标；依次设置上述标题并切换，准备只在截断后部分出现关键词的隐私规则，再准备关键词位于保留部分的规则。分别验证 title_hidden、excluded 后正常退出、导出并断言。规则安装与回调耗时采样缺少公开入口时先使用隔离驱动；`quartz rules check <规则文件>` 只校验文件，不安装规则。

预期事实：标题变化以 `title` 结束旧行，规则生效以 `policy_changed` 切段，`sequence` 增加。挂起目标不会阻塞跨进程标题快照；读取失败可为 `unreadable`，不能用后续标题回填。4,095 单元完整保存；恰好 4,096 时保守为 `truncated`；更长标题截断为最多 4,096，末尾不留未配对高代理项。隐私求值使用截断文本，命中保留部分的隐藏规则后没有 title，excluded 没有 app 或窗口身份；缺口没有应用、标题、域名。自动覆盖 `privacy`、`coverage`、`clock`；人工核对长度、代理项、隐私规则命中解释、回调时间以及日志未输出敏感标题。只在截断点之后的关键词按设计无法命中。

## 13. M1 验收项：02 第 6 节全部场景

前置条件：第 3–12 节逐项记录结果。步骤：列出每个子操作的时间、构建提交、dump 日期和自动断言退出码；检查所有需人工与注入的项目是否已执行。预期：每项都有事实与观察记录；自动规则覆盖见对应节，人工确认通知覆盖、身份、切换误差 P95 < 100 ms、missed_events ≤ 1/小时。未准备的硬件或注入工具登记为待验收。

## 14. M1 验收项：时长守恒

前置条件：每次运行完整的日期集合。步骤：对每个结束场景执行第 2 节断言，对开放核心的冻结快照另执行一次。预期：前台、no_foreground、停止原因并集与缺口在各段的单调范围恰好覆盖；idle 不参与覆盖且独立有效。自动覆盖 `coverage`、`idle`、`clock`、`midnight`；人工核对时间回拨后的重复 UTC 段按顺序保留、睡眠墙上范围与 UTC 午夜片段正确。跨运行空白不纳入单个运行覆盖。

## 15. M1 验收项：十分钟资源回归

前置条件：用户明确留出屏幕，先正常退出本手册启动的核心，保持同一独立 `LOCALAPPDATA`；使用 Windows 版 Deno。此任务会打开一次初始测量界面，随后再开关界面 20 次，用户需要停止其他屏幕操作；按原有脚本执行并预留约 12 分钟。

```powershell
deno task measure --Exe $exe --SettleSeconds 30 --IdleSeconds 600
```

预期：核心 Private Bytes 上限 16 MiB、Private WS 上限 16 MiB、线程上限 12；十分钟空闲 CPU 上限 300 ms；20 次界面开关后核心 Private Bytes 增量 ≤ 2 MiB，界面进程全部退出，核心不加载 `nv*.dll`。按 [08 资源预算](../design/08-resources.md) 同时记录目标值与上限。任务输出未自动判定的 CPU、线程等绝对预算需要人工核对；另用 WPR 录制十分钟空闲、WPA 统计唤醒，要求 ≤ 0.25 次/秒（目标 ≤ 0.1 次/秒）。静态 D3D 导入偏差按 08 §1.1 记录。`acceptance` 只检查此轮留下的事实，不覆盖资源指标。

## 16. M1 验收项：数据库失败、队列满与崩溃恢复

前置条件：第 9、11 节的注入工具和冻结快照。步骤：分别完成各故障，使用普通断言检查恢复后缺口，使用 `--before` 检查所有旧开放行。预期：缺口端点与实际丢失范围一致，旧运行、段与开放事实全部关闭；自动覆盖 `coverage`、`recovery`、`privacy`、`midnight`、`clock`。人工核对故障发生、最后可信边界、恢复复核三个参考时间与持久顺序；网页开放行的恢复属于 M5 接入范围，M1 dump 不输出网页事实。

## 17. M1 验收项：迁移、schema、旧程序拒绝与恢复

前置条件：Windows 工具链、Diesel CLI 2.4.0，使用测试内部临时目录和仓库样本。步骤：执行以下不开窗测试，随后运行 schema 校验。

```powershell
cargo.exe test -p quartz --target-dir target/windows store::tests::fixture_migrates_to_identical_schema_and_keeps_boundary_data
cargo.exe test -p quartz --target-dir target/windows store::tests::newer_database_is_refused_without_modifying_any_database_bytes
cargo.exe test -p quartz --target-dir target/windows store::tests::migration_failure_rolls_back_its_transaction_and_backup_restores
cargo.exe test -p quartz --target-dir target/windows store::tests::released_migration_files_match_lock_and_no_migration_is_unlisted
deno task check-schema
```

预期：样本迁移后 schema 与当前一致；未知迁移版本拒绝写入且原库字节不变；失败事务回滚并能从备份恢复；迁移目录完整符合锁文件。以上由 Rust 测试与 schema 检查断言，`acceptance` 不验证 schema。人工核对每个测试实际执行数量大于零及退出码，测试无误后如需验证恢复 CLI，只对独立数据目录执行 `quartz restore-backup <该目录中的备份> --yes`，先退出核心。

## 18. M1 验收项：Diesel release 体积与增量编译

前置条件：同机器历史 M1-A/M1-B 记录见 [测量记录](../measurements.md)，编译时不运行其他负载。步骤：release 构建后用 `(Get-Item $exe).Length` 记录实际文件字节数；增量编译先跑 `cargo.exe build -p quartz --target-dir target/windows`，在独立工作树只修改一条日志文本，用 `Measure-Command { cargo.exe build -p quartz --target-dir target/windows }` 测秒数，确认只重新编译 quartz，恢复文本并重建。预期：记录引入 Diesel 前后变化；历史 M1-B 为 release +2.036 MiB、debug 增量 9.028 秒。自动断言不覆盖此项，人工核对构建类型、日志、实际改动范围和退出码。

## 19. 一年模拟库查询

前置条件：Windows release、独立新文件。步骤：在 `target\windows\sim` 分别执行 `gen-data --db <新文件> --profile typical --days 365 --seed 1`、heavy 同参数，再分别执行 `bench-query --db <文件> --runs 100`。逐条串行执行，记录生成耗时、数据库大小、行数和 day/week/year P50/P95/max。typical 日、周 P95 要 < 100 ms；year 原始事实读取与年度汇总 < 500 ms 作数值对照，汇总管线在 M2/M4 接入后验收。heavy 同表记录压力读数。具体命令与 E2a 实测值见 [测量记录](../measurements.md)。

当前 dump 没有 `--db`，直接通过 `DataDirectory::resolve` 读取 `Quartz\quartz.db`，因此不对模拟库运行 `deno task acceptance`，也不复制或替换数据库来绕过路径。模拟生成器自身会检查首日、中间日、末日的存储守恒。

## 20. 用户在场与待准备事项

睡眠与唤醒、RDP 断开重连、改系统时间、UAC、Ctrl+Alt+Del、UTC/本地午夜、阈值附近输入，以及显示器和虚拟桌面切换都需要用户安排。资源回归需要空闲屏幕，并会反复开窗。暂停叠加、启动已停止、会话注册失败重试、队列过载、数据库故障、精确提交时机、标题回调延迟与规则安装需要先准备隔离驱动或采样工具。执行结束后退出验收核心并恢复当前 PowerShell 的 `LOCALAPPDATA`。
